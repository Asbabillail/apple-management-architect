# Contributing

Welcome corrections, original explanations, synthetic scenarios and reproducible test results. Reduce an administrator's workload while keeping the evidence honest.

1. Choose one product/task and check the existing coverage and sources.
2. Write an original concise explanation with a current primary source, product/OS applicability, date and retrieval limits. Link vendor documentation; do not copy full manuals or proprietary training material.
3. Label evidence accurately. Supply actual observations for a claimed pilot, or mark NOT_TESTED. An example answer is not a passed evaluation.
4. Add or update a scenario and explain the practical improvement.
5. Remove customer names/domains, account identifiers, inventories, serials, UDIDs, locations, credentials, keys and raw logs. Use synthetic fixtures. Never upload unredacted screenshots.
6. Open a pull request with the problem, change, source and validation. Maintainer review is required before treating a contribution as verified knowledge.

Describe sensitive security issues without details in a public issue; use GitHub private vulnerability reporting if the repository has it enabled. No private reporting channel is configured by this initial package. Do not post secrets while trying to report an exposure.

By contributing original material, you agree to license that contribution under the project's MIT license. Third-party rights remain with their owners.
